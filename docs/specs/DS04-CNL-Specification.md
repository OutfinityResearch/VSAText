# DS04 — CNL Specification

## What is CNL?

CNL (Controlled Natural Language) is SCRIPTA's formal narrative specification language. It is human-readable, machine-parseable, and designed to sit between story planning and prose generation.

In the current product workflow:

- `Book Settings`, `Story Core`, `Narrative Design`, `Blueprint`, and `Story Map` define the story foundation and structure
- `CNL Editor` exposes the resulting formal specification
- `NL Story` uses that specification to generate narrative prose
- `Manuscript` continues the editorial refinement of generated content

In short, CNL sits between planning and prose generation: Book Settings, Blueprint, and Story Map produce the specification; CNL Editor exposes it; NL Story and Manuscript generate and refine content.

Although CNL is readable by humans and editable when needed, it is usually generated by the application rather than written manually from scratch.

## Design Philosophy

CNL follows four design principles:

- **Readability** - authors and developers should be able to inspect a story specification without reading raw JSON
- **Precision** - statements must be specific enough for reliable parsing and validation
- **Composability** - small statements, groups, and patterns should combine into larger specifications
- **Tool-Friendly** - the language must support parsing, AST construction, metrics, validation, export, and prose generation

## Workflow Position

The practical workflow around CNL is:

`New Project -> Book Settings -> Story Core -> Narrative Design -> Blueprint -> Story Map -> CNL Editor -> NL Story -> Manuscript`

The planning pages define intent. The CNL layer formalizes that intent. The prose generation and evaluation layers consume the formalized specification.

This gives CNL three roles:

1. **Specification layer** - a normalized representation of the story plan
2. **Validation layer** - a format the parser and validators can check
3. **Generation layer** - a structured input for NL Story and other generation tools

## Design Model: Dual-Layer CNL

SCRIPTA uses a dual-layer model:

- **SVO layer** - normalized statements used for parsing, metrics, and validation
- **LLM annotation layer** - prose guidance attached to statements, ignored by metrics

### SVO Layer

The SVO layer describes what must be true in the story model:

```cnl
Anna is protagonist
Anna has trait brave
Anna relates to Marcus as sibling
Story has tone hopeful
```

### LLM Annotation Layer

The annotation layer describes how prose should be written or avoided:

```cnl
Anna has trait brave
#hint: Show bravery through action, not declarations.
#avoid: Heroic monologues.

Story has tone hopeful
#style: Understated, concrete sensory detail.
#example: Mercy is shown through costly restraint.
```

Metric calculation and structural validation ignore annotation lines. Prose-generation tools may use them.

Supported annotation markers include:

- `#hint`
- `#example`
- `#style`
- `#avoid`

## Lexical Structure

### Identifiers

Identifiers may be simple or quoted.

#### Simple identifiers

Simple identifiers start with a letter and may contain letters, digits, underscores, and dots.

Examples:

- `Anna`
- `Village`
- `Chapter1`
- `Sc1.2`

#### Quoted identifiers

Quoted identifiers support spaces and punctuation.

Examples:

- `"The Dark Forest"`
- `"inner strength"`
- `"Chapter 1"`

Quoted identifiers are recommended when the UI uses natural labels that do not map cleanly to compact IDs.

### Comments

CNL supports both line comments and block comments:

```cnl
// Single-line comment

/* Multi-line
   comment */
```

Comments are ignored by the parser and must not be confused with LLM annotations.

## Reserved Keywords

The following words are reserved by the language and should not be used as unquoted simple identifiers.

### Core verbs and relation words

- `is`
- `has`
- `relates`
- `includes`
- `references`
- `describes`
- `requires`
- `forbids`
- `must`
- `owns`
- `applies`

### Structural words

- `group`
- `begin`
- `end`

### Property and constraint words

- `trait`
- `tone`
- `max`
- `min`

### Common entity and role words

- `character`
- `location`
- `object`
- `mood`
- `theme`
- `protagonist`
- `antagonist`
- `mentor`
- `ally`
- `enemy`

If such a word must appear as a literal name, use a quoted identifier:

```cnl
"theme" is object
```

## Statement Types

SCRIPTA CNL relies on nine primary statement families.

### 1. Declaration

Pattern:

```cnl
X is Y
```

Examples:

```cnl
Anna is protagonist
Village is location
P1 is pattern
```

### 2. Property Assignment

Pattern:

```cnl
X has Y Z
```

Examples:

```cnl
Anna has trait brave
Story has tone hopeful
Story has max chapters 12
Story has min scenes 6
```

### 3. Relationship

Pattern:

```cnl
X relates to Y as Z
```

Examples:

```cnl
Anna relates to Marcus as sibling
King relates to Council as rival
```

### 4. Inclusion

Pattern:

```cnl
X includes Y Z
```

Examples:

```cnl
Story includes wisdom W1
Sc1 includes character Anna
World includes rule R1
```

### 5. Ownership

Pattern:

```cnl
X owns Y
```

Examples:

```cnl
Anna owns SilverKey
Guild owns ArchiveSeal
```

### 6. Cross-Reference

Pattern:

```cnl
X references @Y
```

Examples:

```cnl
Chapter2 references @Chapter1
Sc4 references @Sc2
```

### 7. Constraints

Patterns:

```cnl
X requires "Y"
X forbids "Y"
X must Y Z
X has tone Y
X has max Y Z
X has min Y Z
```

Examples:

```cnl
Story requires "earned ending"
Story forbids "gratuitous violence"
Chapter1 must introduce Anna
Story has tone reflective
Story has max characters 10
```

### 8. Description

Pattern:

```cnl
X describes "text"
```

Examples:

```cnl
Sc1 describes "Rain presses against the shutters."
Artifact1 describes "A silver key etched with ash-black runes."
```

### 9. Events and Action Statements

Any valid event-like statement that uses another verb may be preserved as an action or event statement in the AST.

Examples:

```cnl
Anna discovers SilverKey
Marcus betrays Anna
Storm engulfs Harbor
```

These statements are especially useful for scene-level structure and prose planning.

## Groups and Hierarchical Structure

Groups define hierarchical story scope. The canonical hierarchy is:

`Book -> Chapter -> Scene`

### Basic group syntax

```cnl
Book group begin
  Chapter1 group begin
    Scene1 group begin
      Anna discovers SilverKey
    Scene1 group end
  Chapter1 group end
Book group end
```

### Quoted group names

```cnl
"Book" group begin
  "Chapter 1" group begin
    "Scene 1.1" group begin
      Anna discovers SilverKey
    "Scene 1.1" group end
  "Chapter 1" group end
"Book" group end
```

### Group rules

- nesting must be structurally correct
- every `group begin` must have a matching `group end`
- the group identifier on `begin` and `end` must match
- chapter-local and scene-local statements live inside their corresponding groups
- invalid nesting is a parser error

## Entity Model

Common entity types used in SCRIPTA include:

- `protagonist`
- `antagonist`
- `mentor`
- `ally`
- `enemy`
- `character`
- `location`
- `object`
- `theme`
- `mood`
- `world_rule`
- `wisdom`
- `pattern`

Stable identifiers are recommended for reusable spec items, especially:

- world rules: `R1`, `R2`
- wisdom items: `W1`, `W2`
- patterns: `P1`, `P2`

## Pattern System

Patterns define reusable narrative templates with variable placeholders.

### Pattern declaration

```cnl
P1 is pattern
P1 has label "Hero's Call"
P1 has variable $hero as character
P1 has variable $location as location
P1 has variable $challenge as object

P1 has template begin
  $hero is at $location
  $hero discovers $challenge
  $hero must confront fear
P1 has template end
```

### Pattern instantiation

```cnl
Sc1 uses pattern P1
Sc1 binds $hero to Anna
Sc1 binds $location to Village
Sc1 binds $challenge to SilverKey
```

### Complete reusable example

```cnl
P2 is pattern
P2 has label "Hero's Call"
P2 has variable $hero as character
P2 has variable $mentor as character
P2 has variable $location as location

P2 has template begin
  $hero is at $location
  $mentor relates to $hero as guide
  $hero discovers "call to adventure"
  $hero describes "hesitation before action"
P2 has template end

Scene1 uses pattern P2
Scene1 binds $hero to Anna
Scene1 binds $mentor to Mira
Scene1 binds $location to Harbor
```

Patterns are intended to be reusable across stories, chapters, and scenes depending on the pattern category.

## AST and Parser Output

The parser converts CNL into a structured AST that downstream tools interpret.

The AST commonly contains:

- `entities`
- `groups`
- `relationships`
- `ownership`
- `constraints`
- `references`
- `annotations`
- action or event statements

### Example entity representation

```json
{
  "Anna": {
    "type": "protagonist",
    "properties": {
      "trait": ["brave", "doubtful"]
    }
  }
}
```

### Example group representation

```json
{
  "id": "Chapter1",
  "kind": "group",
  "children": [
    {
      "id": "Scene1",
      "kind": "group"
    }
  ]
}
```

### Example relationship representation

```json
{
  "source": "Anna",
  "target": "Marcus",
  "type": "sibling"
}
```

### Example constraint representation

```json
{
  "scope": "Story",
  "kind": "requires",
  "value": "earned ending"
}
```

Metrics are calculated by interpreting the AST, not by re-reading raw lines as plain text.

## Semantic Rules and Validation

The parser and validators should enforce these essential rules.

### Declaration before use

Entities should be declared before they are referenced in ownership, relationships, includes, or actions.

### Cumulative properties

Properties are cumulative unless a tool explicitly normalizes them.

Example:

```cnl
Anna has trait brave
Anna has trait doubtful
```

Both traits remain attached to `Anna`.

### Scope rules

- `Story` and `World` statements are global
- `Chapter` statements are chapter-local
- `Scene` statements are scene-local

Local scope may refine global context, but should not silently invalidate it.

### Reference and ownership validation

- `X owns Y` requires both `X` and `Y` to be known entities
- `X references @Y` requires `Y` to exist as a known group or identifier

### Group validation

- nested groups must be balanced
- `begin` and `end` names must match
- illegal crossing of scopes is invalid

### Constraint consistency

The system must detect contradictions such as:

```cnl
Story requires "romance"
Story forbids "romance"
```

The same applies when `must`, `requires`, or structural limits conflict.

## Common Patterns and Subplots

Typical reusable CNL fragments include:

- **Character introduction** - first appearance, trait setup, visible goal
- **Location setup** - atmosphere, world-rule implications, local stakes
- **Scene templates** - discovery, confrontation, revelation, aftermath
- **Subplots** - recurring secondary threads such as romance, betrayal, or mentorship

Example subplot sketch:

```cnl
S1 is subplot
S1 has label "Anna and Marcus"
S1 has category romance
S1 includes character Anna
S1 includes character Marcus
S1 has touchpoint "Chapter1.Scene1"
S1 has touchpoint "Chapter2.Scene2"
```

## Common Errors

Typical parser and validation errors include:

| Error | Meaning | Typical fix |
|-------|---------|-------------|
| Undefined entity | A relationship, ownership, or include references something undeclared | Declare the entity earlier |
| Unclosed group | A `group begin` does not have a matching `group end` | Close the missing group |
| Invalid verb | The statement does not match a supported statement form | Use a valid statement pattern |
| Conflicting constraints | The specification both requires and forbids the same thing, or introduces contradictory limits | Remove or reconcile the conflict |
| Syntax error | Tokens or quoting are malformed | Fix quoting, spacing, or structure |

## API Usage

CNL parsing is available in both browser-safe and Node entrypoints.

### Browser / portable usage

```javascript
import { parseCNL, extractEntities, extractConstraints } from './src/index.mjs';

const cnlText = `
Anna is protagonist
Story has tone hopeful
`;

const result = parseCNL(cnlText);

if (!result.valid) {
  console.error(result.errors);
} else {
  console.log(result.ast);
  console.log(extractEntities(result.ast));
  console.log(extractConstraints(result.ast));
}
```

### Direct parser usage

```javascript
import { parseCNL, extractEntities, extractConstraints } from './src/cnl-parser/cnl-parser.mjs';

const result = parseCNL('Anna is protagonist');

if (result.valid) {
  const entities = extractEntities(result.ast);
  const constraints = extractConstraints(result.ast);
  console.log(entities, constraints);
}
```

### Node.js usage

```javascript
import SDK, { parseCNL, extractEntities, extractConstraints } from './src/index-node.mjs';

const result = parseCNL('Anna is protagonist');

if (!result.valid) {
  console.error(result.errors);
} else {
  console.log(extractEntities(result.ast));
  console.log(extractConstraints(result.ast));
}
```

### Expected parse result

The parser result should be treated as a structured object with at least:

- `valid`
- `ast`
- `errors`
- `warnings`

The downstream evaluation and generation layers should always check parser validity before consuming the AST.
