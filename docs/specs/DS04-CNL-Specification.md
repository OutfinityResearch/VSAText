## What is CNL?
<!-- {"achilles-ide-paragraph":{"id":"paragraph-0665ebe6-f28b-4275-9a32-ec486b84a6ad","type":"markdown","title":"Paragraph 1"}} -->
CNL (Controlled Natural Language) is SCRIPTA's formal narrative specification language. It is human-readable, machine-parseable, and designed to sit between story planning and prose generation.

In the current product workflow:

- `New Project` creates the project foundation
- `Blueprint` defines the structural story plan
- `CNL Editor` exposes the resulting formal specification
- `NL Story` uses that specification to generate narrative prose
- `Manuscript` continues the editorial refinement of generated content

In short, CNL sits between structural planning and prose generation: Blueprint produces the formal story structure, CNL Editor exposes it, and NL Story plus Manuscript generate and refine prose from it.

Although CNL is readable by humans and editable when needed, it is usually generated by the application rather than written manually from scratch.

## Design Philosophy
<!-- {"achilles-ide-paragraph":{"id":"paragraph-784f6936-51e2-4a4e-b66d-b16db22479f5","type":"markdown","title":"Paragraph 1"}} -->
CNL follows four design principles:

- **Readability** - authors and developers should be able to inspect a story specification without reading raw JSON
- **Precision** - statements must be specific enough for reliable parsing and validation
- **Composability** - small statements, groups, and patterns should combine into larger specifications
- **Tool-Friendly** - the language must support parsing, AST construction, metrics, validation, export, and prose generation

## Workflow Position
<!-- {"achilles-ide-paragraph":{"id":"paragraph-2e1e6453-646e-448f-b3c2-1e83e24ddd5f","type":"markdown","title":"Paragraph 1"}} -->
The practical workflow around CNL is:

`New Project -> Blueprint -> CNL Editor -> NL Story -> Manuscript`

Blueprint defines the structural plan. The CNL layer formalizes that plan into a portable specification. The prose generation and evaluation layers consume the formalized specification.

This gives CNL three roles:

1. **Specification layer** - a normalized representation of the story plan
2. **Validation layer** - a format the parser and validators can check
3. **Generation layer** - a structured input for NL Story and other generation tools

## Blueprint to CNL Mapping
<!-- {"achilles-ide-paragraph":{"id":"paragraph-06f978b7-6027-4046-8449-4287880b3dfe","type":"markdown","title":"Paragraph 1"}} -->
In the current application model, Blueprint is the authoritative structural editor and CNL is the formalized output of that structure.

- `Blueprint.arc` determines the narrative arc used in the specification.
- `Blueprint.beatMappings` determine which beats exist and which scenes they target.
- `Blueprint.tensionCurve` contributes pacing and structural pressure data.
- `Blueprint.hooks` contribute opening and mid-story hook targets.
- scene structure and dialogue libraries contribute chapter, scene, and dialogue sections.

This means CNL is not just a text export. It is the formal projection of the current project state.

When Blueprint changes, CNL should change as well.

- changing the arc updates beat mappings
- arc-dependent dialogue beat links are synchronized
- hook beat targets are synchronized
- auto-generated structural titles may change when they are still derived from beats

## CNL Syntax Reference
<!-- {"achilles-ide-paragraph":{"id":"paragraph-c375d693-4263-4b5e-b424-6411a460fc83","type":"markdown","title":"Paragraph 1"}} -->
This chapter is the canonical syntax reference for SCRIPTA CNL.

SCRIPTA is **SVO-first** (Subject-Verb-Object) for machine-parseable semantics, plus:

- a small set of planning-oriented lines for `Blueprint`, `Dialogue`, and `Subplot` data
- an annotation layer (`#hint`, `#example`, `#style`, `#avoid`) used for prose guidance and ignored by metrics


<!-- {"achilles-ide-chapter":{"id":"chapter-26b1acee-f956-4b19-b8cf-0bd03752662e","title":"Syntax Overview","anchorId":"chapter-chapter-26b1acee-f956-4b19-b8cf-0bd03752662e"}} -->

### Syntax Overview
<!-- {"achilles-ide-paragraph":{"id":"paragraph-96938fc8-2d68-4849-aec7-d0054be1a23a","type":"markdown","title":"Paragraph 1"}} -->


<!-- {"achilles-ide-chapter":{"id":"chapter-a4da30b5-ff37-4399-8d9f-64c3f2033146","title":"Core statement types","anchorId":"chapter-chapter-a4da30b5-ff37-4399-8d9f-64c3f2033146"}} -->
<a id="chapter-chapter-a4da30b5-ff37-4399-8d9f-64c3f2033146"></a>
#### Core statement types
<!-- {"achilles-ide-paragraph":{"id":"paragraph-e20cf595-0336-46db-aa38-f5a47e6ad08f","type":"markdown","title":"Paragraph 1"}} -->
```cnl
// Entity declaration
Subject is Type
Anna is protagonist

// Property assignment
Subject has Property Value
Anna has trait courage

// Relationship
Subject relates to Target as Type
Anna relates to Marcus as sibling

// Constraints
Subject requires "value"
Subject forbids "value"
Subject must Action Target

// Ownership
Subject owns Object
Anna owns SilverKey

// Tone and limits
Subject has tone Value
Subject has max Property Count
Subject has min Property Count
```

#### Blueprint, dialogue, and subplot extensions
<!-- {"achilles-ide-paragraph":{"id":"paragraph-efb22b78-46e2-44a4-8ac8-360fdb5ff05e","type":"markdown","title":"Paragraph 1"}} -->

```cnl
Blueprint uses arc heros_journey

call_to_adventure has tension 2
call_to_adventure has mood mysterious
call_to_adventure has note "Herald delivers the message"

D3 has tension 4

  Anna says intent "demand truth"
  Anna says emotion anger
  Anna says sketch "You knew. All this time, you knew."
D3 exchange end

Subplot S1 type romance
S1 involves Anna
S1 starts at beat crossing_threshold
S1 resolves at beat return
```

## Design Model: Dual-Layer CNL
<!-- {"achilles-ide-paragraph":{"id":"paragraph-3283b061-d24b-493b-8b3f-c63eeeb993f4","type":"markdown","title":"Paragraph 1"}} -->
SCRIPTA uses a dual-layer model:

- **SVO layer** - normalized statements used for parsing, metrics, and validation
- **LLM annotation layer** - prose guidance attached to statements, ignored by metrics


<!-- {"achilles-ide-chapter":{"id":"chapter-e4cd089f-16ce-44e5-ad8d-a605a1713234","title":"SVO Layer","anchorId":"chapter-chapter-e4cd089f-16ce-44e5-ad8d-a605a1713234"}} -->
<a id="chapter-chapter-e4cd089f-16ce-44e5-ad8d-a605a1713234"></a>
### SVO Layer
<!-- {"achilles-ide-paragraph":{"id":"paragraph-f61d1dc8-db00-4d1f-aa91-4354ccd42e2c","type":"markdown","title":"Paragraph 1"}} -->
The SVO layer describes what must be true in the story model:

```cnl
Anna is protagonist
Anna has trait brave
Anna relates to Marcus as sibling
Story has tone hopeful
```


<!-- {"achilles-ide-chapter":{"id":"chapter-1080f7da-6106-492e-911b-104889ca892a","title":"LLM Annotation Layer","anchorId":"chapter-chapter-1080f7da-6106-492e-911b-104889ca892a"}} -->
<a id="chapter-chapter-1080f7da-6106-492e-911b-104889ca892a"></a>
### LLM Annotation Layer
<!-- {"achilles-ide-paragraph":{"id":"paragraph-d91f217d-ed36-4905-a24c-c86050c5e34d","type":"markdown","title":"Paragraph 1"}} -->
The annotation layer describes how prose should be written or avoided:

```cnl
Anna has trait brave
#hint: Show bravery through action, not declarations.
#avoid: Heroic monologues.

Story has tone hopeful
#style: Understated, concrete sensory detail.
#example: Mercy is shown through costly restraint.
```

Metric calculation and structural validation ignore annotation lines. Prose-generation tools may use them.

Supported annotation markers include:

- `#hint`
- `#example`
- `#style`
- `#avoid`

### Identifiers
<!-- {"achilles-ide-paragraph":{"id":"paragraph-8da11566-d0ef-4be0-9010-7a6a1efe4876","type":"markdown","title":"Paragraph 1"}} -->
Identifiers may be simple or quoted.


<!-- {"achilles-ide-chapter":{"id":"chapter-af83eb31-128d-4bbe-8331-8c7c772c569e","title":"Simple identifiers","anchorId":"chapter-chapter-af83eb31-128d-4bbe-8331-8c7c772c569e"}} -->

#### Simple identifiers
<!-- {"achilles-ide-paragraph":{"id":"paragraph-2d292465-2216-46d9-9d03-9dbeb56ddba9","type":"markdown","title":"Paragraph 1"}} -->
Simple identifiers start with a letter and may contain letters, digits, underscores, and dots.

Examples:

- `Anna`
- `Village`
- `Chapter1`
- `Sc1.2`


<!-- {"achilles-ide-chapter":{"id":"chapter-b2e324e5-f22c-4afa-81a5-9b7512724e01","title":"Quoted identifiers","anchorId":"chapter-chapter-b2e324e5-f22c-4afa-81a5-9b7512724e01"}} -->
<a id="chapter-chapter-b2e324e5-f22c-4afa-81a5-9b7512724e01"></a>
#### Quoted identifiers
<!-- {"achilles-ide-paragraph":{"id":"paragraph-fb956b93-0d66-4b2e-a876-e19b5c9dfb19","type":"markdown","title":"Paragraph 1"}} -->
Quoted identifiers support spaces and punctuation.

Examples:

- `"The Dark Forest"`
- `"inner strength"`
- `"Chapter 1"`

Quoted identifiers are recommended when the UI uses natural labels that do not map cleanly to compact IDs.


<!-- {"achilles-ide-chapter":{"id":"chapter-97a9ec9a-651f-473c-a474-1c78133a8eeb","title":"Comments","anchorId":"chapter-chapter-97a9ec9a-651f-473c-a474-1c78133a8eeb"}} -->
<a id="chapter-chapter-97a9ec9a-651f-473c-a474-1c78133a8eeb"></a>
### Comments
<!-- {"achilles-ide-paragraph":{"id":"paragraph-5e840ca2-40d4-4c95-875b-7fbffcb17d4f","type":"markdown","title":"Paragraph 1"}} -->
CNL supports both line comments and block comments:

```cnl
// Single-line comment

/* Multi-line
   comment */
```

Comments are ignored by the parser and must not be confused with LLM annotations.

### Group rules
<!-- {"achilles-ide-paragraph":{"id":"paragraph-1fae66a8-adfb-4c9e-9c0a-49b0fc6c75d3","type":"markdown","title":"Paragraph 1"}} -->
- nesting must be structurally correct
- every `group begin` must have a matching `group end`
- the group identifier on `begin` and `end` must match
- chapter-local and scene-local statements live inside their corresponding groups
- invalid nesting is a parser error

<!-- {"achilles-ide-paragraph":{"id":"paragraph-7fab784c-93d4-4f8a-80b6-f5b388219724","type":"markdown","title":"Paragraph 1"}} -->
The following example reflects the current product workflow more realistically.

Marcus has trait loyal

Rowan has trait calculating

Anna relates to Rowan as rival

Harbor has atmosphere tense
"The Old Tower" is location
"The Old Tower" has atmosphere haunted

// Objects

Anna owns SilverKey

// Blueprint-derived planning
Blueprint is blueprint
Blueprint uses arc heros_journey
IncitingIncident is beat
Midpoint is beat
Climax is beat
IncitingIncident has tension 2
Midpoint has tension 4
Climax has tension 5

## AST and Parser Output
<!-- {"achilles-ide-paragraph":{"id":"paragraph-0710d490-0b54-46f2-a3d3-010fc10eb056","type":"markdown","title":"Paragraph 1"}} -->
The parser converts CNL into a structured AST that downstream tools interpret.

The AST commonly contains:

- `entities`
- `groups`
- `relationships`
- `ownership`
- `constraints`
- `references`
- `annotations`
- `blueprint planning data`
- `dialogue metadata`
- action or event statements

## UI Representation
<!-- {"achilles-ide-paragraph":{"id":"paragraph-f3698192-2928-476c-b8d4-e5f2ba24b4c7","type":"markdown","title":"Paragraph 1"}} -->
The CNL page has two complementary roles in the product:

1. **Visual review mode** - a formatted CNL view organized into sections such as beat mappings, hooks, dialogues, and book structure
2. **Direct text mode** - editable CNL text for precise corrections, import, export, and debugging

For readability, the visual CNL view may present simplified display labels that differ from internal project IDs.

Example:

- internal dialogue id: `dlg_b4dacf37ad22`
- visual display label: `D1`

This display convention improves review clarity but does not change the underlying stored identifier.

## Semantic Rules and Validation
<!-- {"achilles-ide-paragraph":{"id":"paragraph-37e689f9-aaf8-4e00-bffa-5034697f08fc","type":"markdown","title":"Paragraph 1"}} -->
The parser and validators should enforce these essential rules.


<!-- {"achilles-ide-chapter":{"id":"chapter-fcc6ef85-cc3d-4087-bc70-31ce2148e8db","title":"Declaration before use","anchorId":"chapter-chapter-fcc6ef85-cc3d-4087-bc70-31ce2148e8db"}} -->
<a id="chapter-chapter-fcc6ef85-cc3d-4087-bc70-31ce2148e8db"></a>
### Declaration before use
<!-- {"achilles-ide-paragraph":{"id":"paragraph-0369b71e-f49d-4046-94be-8970c2b1569c","type":"markdown","title":"Paragraph 1"}} -->
Entities should be declared before they are referenced in ownership, relationships, includes, or actions.


<!-- {"achilles-ide-chapter":{"id":"chapter-4f925413-f2a0-4dde-88e0-b5d060963fcf","title":"Cumulative properties","anchorId":"chapter-chapter-4f925413-f2a0-4dde-88e0-b5d060963fcf"}} -->
<a id="chapter-chapter-4f925413-f2a0-4dde-88e0-b5d060963fcf"></a>
### Cumulative properties
<!-- {"achilles-ide-paragraph":{"id":"paragraph-75d9af9a-7d7a-4ec8-89fd-719aaaf1d3fb","type":"markdown","title":"Paragraph 1"}} -->
Properties are cumulative unless a tool explicitly normalizes them.

Example:

```cnl
Anna has trait brave
Anna has trait doubtful
```

Both traits remain attached to `Anna`.


<!-- {"achilles-ide-chapter":{"id":"chapter-7567fb38-4992-4955-8818-56e8de7cfbc4","title":"Scope rules","anchorId":"chapter-chapter-7567fb38-4992-4955-8818-56e8de7cfbc4"}} -->
<a id="chapter-chapter-7567fb38-4992-4955-8818-56e8de7cfbc4"></a>
### Scope rules
<!-- {"achilles-ide-paragraph":{"id":"paragraph-95400f59-3822-40ba-bf54-15f79c8f673b","type":"markdown","title":"Paragraph 1"}} -->
- `Story` and `World` statements are global
- `Chapter` statements are chapter-local
- `Scene` statements are scene-local

Local scope may refine global context, but should not silently invalidate it.


<!-- {"achilles-ide-chapter":{"id":"chapter-53403a27-5bcb-42c4-bcc2-cfab8ee9e43b","title":"Reference and ownership validation","anchorId":"chapter-chapter-53403a27-5bcb-42c4-bcc2-cfab8ee9e43b"}} -->
<a id="chapter-chapter-53403a27-5bcb-42c4-bcc2-cfab8ee9e43b"></a>
### Reference and ownership validation
<!-- {"achilles-ide-paragraph":{"id":"paragraph-87193f16-e777-4af9-a985-0b9eb112cf26","type":"markdown","title":"Paragraph 1"}} -->
- `X owns Y` requires both `X` and `Y` to be known entities
- `X references @Y` requires `Y` to exist as a known group or identifier


<!-- {"achilles-ide-chapter":{"id":"chapter-ed3a1e46-93f6-4c29-bfc8-23851d7bf778","title":"Group validation","anchorId":"chapter-chapter-ed3a1e46-93f6-4c29-bfc8-23851d7bf778"}} -->
<a id="chapter-chapter-ed3a1e46-93f6-4c29-bfc8-23851d7bf778"></a>
### Group validation
<!-- {"achilles-ide-paragraph":{"id":"paragraph-95cee048-f2db-485c-8691-1622be921842","type":"markdown","title":"Paragraph 1"}} -->
- nested groups must be balanced
- `begin` and `end` names must match
- illegal crossing of scopes is invalid


<!-- {"achilles-ide-chapter":{"id":"chapter-b80344cc-2723-44cf-bfb6-71cceacc0054","title":"Constraint consistency","anchorId":"chapter-chapter-b80344cc-2723-44cf-bfb6-71cceacc0054"}} -->
<a id="chapter-chapter-b80344cc-2723-44cf-bfb6-71cceacc0054"></a>
### Constraint consistency
<!-- {"achilles-ide-paragraph":{"id":"paragraph-8f5d31d8-d44b-4266-ab6d-9cf92f443e3d","type":"markdown","title":"Paragraph 1"}} -->
The system must detect contradictions such as:

```cnl
Story requires "romance"
Story forbids "romance"
```

The same applies when `must`, `requires`, or structural limits conflict.

## Common Patterns and Subplots
<!-- {"achilles-ide-paragraph":{"id":"paragraph-87f1a8d0-d515-420d-8947-301dc353b4d6","type":"markdown","title":"Paragraph 1"}} -->
Typical reusable CNL fragments include:

- **Character introduction** - first appearance, trait setup, visible goal
- **Location setup** - atmosphere, world-rule implications, local stakes
- **Scene templates** - discovery, confrontation, revelation, aftermath
- **Subplots** - recurring secondary threads such as romance, betrayal, or mentorship

Example subplot sketch:

```cnl
S1 is subplot
S1 has label "Anna and Marcus"
S1 has category romance
S1 includes character Anna
S1 includes character Marcus
S1 has touchpoint "Chapter1.Scene1"
S1 has touchpoint "Chapter2.Scene2"
```

## Common Errors
<!-- {"achilles-ide-paragraph":{"id":"paragraph-68427cb8-af41-4b88-b06b-de67218303f1","type":"markdown","title":"Paragraph 1"}} -->
Typical parser and validation errors include:

| Error | Meaning | Typical fix |
|-------|---------|-------------|
| Undefined entity | A relationship, ownership, or include references something undeclared | Declare the entity earlier |
| Unclosed group | A `group begin` does not have a matching `group end` | Close the missing group |
| Invalid verb | The statement does not match a supported statement form | Use a valid statement pattern |
| Conflicting constraints | The specification both requires and forbids the same thing, or introduces contradictory limits | Remove or reconcile the conflict |
| Syntax error | Tokens or quoting are malformed | Fix quoting, spacing, or structure |

### Expected parse result
<!-- {"achilles-ide-paragraph":{"id":"paragraph-7d9ec10e-27f9-4a71-aa7c-1cb6e8cb9a2e","type":"markdown","title":"Paragraph 1"}} -->
The parser result should be treated as a structured object with at least:

- `valid`
- `ast`
- `errors`
- `warnings`

The downstream evaluation and generation layers should always check parser validity before consuming the AST.
